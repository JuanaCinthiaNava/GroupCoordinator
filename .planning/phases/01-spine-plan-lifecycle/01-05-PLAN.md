<objective>
Wire the anonymous-to-authenticated upgrade vertical slice + signed-in user dashboard. After this plan: an anonymous guest viewing a plan can tap "Continuar con Google", complete OAuth, and land back on the same plan with their session upgraded (no context loss, no separate "joining" step), the plan_members row inserted with the role from the invite token; and signed-in users have a `/me` dashboard listing every plan they belong to.

Purpose: Closes AUTH-02, AUTH-04, AUTH-05, PLAN-06. This is the moment Phase 1's spine becomes whole — the hybrid auth model from CONTEXT.md (anonymous view → OAuth upgrade without context loss) is now end-to-end. CP-1 (weakest-link adoption) is fully mitigated only when this plan ships.

**Scope acknowledgments (deliberate omissions):**
- **D-12 (no pending-action replay in v1):** the OAuth callback does NOT replay any pending intent (e.g., a vote click the guest attempted before signing in). Phase 1 has no interactive surfaces beyond the sign-in CTA itself, so there's no intent to replay. When Phase 4 (voting) and Phase 2/5 (edit surfaces) ship, they can add their own intent persistence — Phase 1 deliberately ships without it.
- **D-17 (no magic-link auth in Phase 1):** the sign-in bottom sheet (Surface 5) offers exactly one provider — "Continuar con Google". No "Or sign in with email" option, no magic-link alternative. Apple OAuth (AUTH-03) was deferred to v2 (CONTEXT.md D-16), and magic-link is the iOS contingency only if Phase 7 telemetry shows iOS dropoff.

Output: One sign-in page (Surface 5) + one OAuth callback route + one sign-out route + /me page (Surface 7) + plan card component + header user menu + 3 test specs.

User story (MVP_MODE): **As an** anonymous viewer of a shared plan, **I want to** tap one button to sign in with Google and end up exactly where I was (same plan, same scroll position best-effort), **so that** I can participate in the plan without losing my place.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Anonymous user → /auth/sign-in → Google → /auth/callback | OAuth redirect chain must preserve the anonymous user_id; cookies must be set on the redirect response |
| Server (callback) → invite_tokens lookup | Service-role bypasses RLS to read the role; must NOT expose token to the user |
| Browser → /auth/sign-out | Must reject GET to avoid drive-by sign-outs via image src or pre-fetched links |
| Authenticated client → /me | RLS filters; anonymous → redirect |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Spoofing | Forged `next` param in /auth/callback redirects to attacker site | mitigate | Validate `next` is a relative path (starts with `/`, no `//` prefix) before passing to `NextResponse.redirect`; reject `http://` / `https://` schemes; fall back to `/me` |
| T-05-02 | Repudiation | Sign-out via GET (drive-by attack) | mitigate | Sign-out route rejects all methods except POST; HeaderUserMenu uses `<form method="post">` |
| T-05-03 | Information Disclosure | linkIdentity fails silently and user gets a NEW user_id, breaking plan_members membership | mitigate | Callback explicitly checks that `data.user.id` is non-null after exchange; if linkIdentity collision detected (Assumption A1 / A2), redirect to recovery copy; integration test asserts the extracted helper handles the error cases |
| T-05-04 | Information Disclosure | Service-role used in callback could read OTHER users' app_metadata if userId comes from user input | mitigate | userId comes from `data.user.id` after exchangeCodeForSession — server-validated session, not request body |
| T-05-05 | Elevation of Privilege | plan_members upsert uses service-role, bypassing the plan_members_insert_self_or_owner RLS policy | accept | Server-side after server-validated session; service-role is the correct tool when RLS would re-execute the same check.
